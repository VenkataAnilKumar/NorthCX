# NorthCX Model Providers

Status: **Partly built**. Updated: 2026-11-18. Master for: the model interface and providers. WP1.1 to WP1.5 and the core of WP1.9 and WP1.10 are done: the interface, the registry, Claude with two clients, an OpenAI-compatible provider, the providers file, currency budgets, and per-request model choice by data policy and routing rules. Per-agent qualification (WP1.11) is built too. The Admin screens (WP1.12) and the experimental routers (WP1.7, WP1.13) are still planned (E1). How a model is chosen is in `NorthCX_Hybrid-Model-Selection.md`.

## How models are called today (built)
NorthCX calls Claude through Anthropic's official SDK by default, or through its own direct HTTPS client. The SDK was a deliberate first step: it gives correct handling of the API (authentication, streaming formats, error types, new model features) with the least code to own.

The SDK is **isolated behind one interface**. The runtime, supervisors, simulations, summarisation, judge and every other part depend only on `LLM.complete(LLMRequest) -> LLMResponse` (`northcx/types.py`). The only module that imports the SDK is `northcx/providers/anthropic.py` (`AnthropicLLM`, re-exported from `northcx/llm.py`); a test fails if any other module does. Retries, fallback models, timeouts, circuit breaking and budgets (`ReliableLLM`, `UsageLedger`) wrap any backend, so they work unchanged for any provider added later.

## The provider layer (built, 1.1 work in progress)
`northcx/providers/` holds the shared types and the registry:
- **`Provider`** (`base.py`): `name`, `default_model`, `capabilities` (tools, parallel tools, images, documents, context size), `prices` (per million tokens, supplied by the operator, never guessed) and `complete`. Errors are `ProviderError` with a `status_code` (plus `ProviderTimeout` and `ProviderUnreachable`, which `is_transient` already treats as retryable); messages never contain keys or request bodies.
- **`ProviderRegistry`** (`registry.py`): implements the same `LLM` interface, so it drops in wherever a model backend is used (including `ReliableLLM`). Models are named `provider:model`; a name whose prefix is not a registered provider is a bare model name and goes to the default provider (so existing agents and `llama3:8b`-style names are unchanged). `require_tools` refuses an agent with tools on a model that cannot call them.
- **Claude, two clients** (`anthropic.py`): the SDK (default) and a direct HTTPS client (`NORTHCX_ANTHROPIC_CLIENT=http`). One conformance test file runs both: plain reply with usage and the answering model, tool call, tool-result round trip, no tools sent when none are declared, status codes and transient classification, timeouts, key placement.
Built since this line was first written: the OpenAI-compatible provider (which covers local servers such as Ollama), the providers file and budgets in currency (next section). Not built yet: fallback chains across providers with capability checks at release time. Live simulations use the configured providers both from the command line (`--model live`) and through the server (`POST /v1/simulations/runs`, the Studio Simulations page); both build them with `northcx/providers/setup.py`. Running local models: `NorthCX_Local-Models-Guide.md`. The product is hybrid (decision 198).

## Providers file, budgets and routing (built, Phase 2 of the implementation plan)
- **OpenAI-compatible provider** (`northcx/providers/openai_compat.py`): any server that speaks the chat-completions format (hosted services, vLLM, Ollama, llama.cpp, LM Studio, gateways). Messages, tool calls, tool results and images are translated at the edge; errors carry the HTTP status so retries stay correct; the key goes in a header and never appears in an error. Plain http is refused unless the address is localhost or the operator sets `allowInsecureHttp` for a trusted network.
- **Providers file** (`NORTHCX_PROVIDERS_FILE`, YAML): each provider has a name (used in `name:model`), a type (`openai-compatible` or `anthropic`), a base URL, a key by environment variable or file (a key written in the file is refused), a default model, capabilities, per-model prices with a currency, and a tier (`local`, `private-cloud`, `public-cloud`). With a providers file the Anthropic key is optional.
- **Budgets in currency:** `NORTHCX_DAILY_BUDGET` (an amount) and `NORTHCX_BUDGET_CURRENCY` (default USD). Every answer is costed from the operator's own prices and counted per agent per UTC day (shared across processes with the postgres limits backend); at the limit, model calls stop and conversations go to people. The server refuses to start with a budget if any provider's default model has no price in the budget currency; an answer from a model with no price in that currency is flagged `unpriced` in the trace and counted as zero, so give every model you use a price.
- **Choosing a model per request** (`NORTHCX_ROUTING_RULES_FILE`, YAML; see `NorthCX_Hybrid-Model-Selection.md`): hard data constraints first, then the operator's ordered rules, then the fallback chain restricted to the allowed tiers. A conversation is sensitive when the agent is marked `sensitive`, the customer is identity-verified, personal data appears, or a configured topic word appears; once sensitive it stays sensitive. Sensitive conversations may use only the tiers the policy lists (public cloud is not listed by default; an administrator may name agents that may use it). Calls with no conversation context (for example administrator tools) are treated as sensitive. If no model is allowed the conversation goes to a person. Each answer's trace carries a `model_choice` event: the model, its tier, the rule that chose it and every model skipped with the reason. - **Qualification** (`qualification: {required: true}` in the routing file; decision 164): a model may serve an agent's customers only after it passed that agent's required scenarios (all of them) and at least 90 percent of its other scenarios, for the agent's exact current definition. Run the agent on the candidate with `POST /v1/simulations/runs` (`agent`, `version`, `model`, `mode: live`), then record the result with `POST /v1/agents/{id}/qualifications` (`model`, `runId`; needs the scenarios:require permission; audited). Change the prompt or tools and the digest changes, so the model must be qualified again; a later failing run withdraws it. `exempt` lists models trusted without a run. Evaluation runs may always use a model; internal calls with no agent are not an agent's customers. `GET /v1/agents/{id}/qualifications` lists the history.
- **Eligible set:** the models named by a rule, the request or the fallbacks come first, then each provider's own default as a last resort, all inside the allowed tiers.

Without the routing file nothing changes.

## Planned: the rest (E1)
The remaining steps. Built already: item 1 (as an option), the provider-qualified names of item 4 and the capability declarations of item 5 (`require_tools` refuses an agent with tools on a model without them). Still to do: items 2 and 3, fallback chains across providers, and checking capabilities at release time:

1. **Direct Claude client** (built as an option; the SDK stays the default until parity is proven live). Call the Claude Messages API over HTTPS ourselves (the request and response shapes are already what the runtime uses), keeping the SDK only until parity is proven by the existing test suite and a live comparison.
2. **Provider adapters.** One small adapter per provider (for example an OpenAI-compatible one that also covers many self-hosted models). Each translates between NorthCX's neutral request and the provider's format.
3. **Neutral message format.** Messages and tool calls currently use Claude's block shapes (`text`, `tool_use`, `tool_result`). When a second provider arrives, that shape stays as NorthCX's own neutral format and each adapter translates at its edge; the runtime does not change.
4. **Per-agent and per-purpose model choice.** An agent already names a model (`model`), and summaries and the judge accept their own. Model names can already be qualified by provider (`anthropic:claude-...`); with several providers the fallback chain may mix providers.
5. **Capabilities.** Providers differ in tool calling, parallel calls, token reporting, context size and cost. Each adapter will declare what it supports so the platform can refuse a configuration that cannot work (for example an agent that needs tools on a model that has none) instead of failing in a conversation.

## Rules for adapters
- Return `usage` (input and output tokens) so budgets work, and report the model that actually answered.
- Raise errors that carry an HTTP-style `status_code` where the provider has one, so retry and fallback decisions stay correct (`is_transient`).
- Never put credentials in errors, traces or logs; read them through the secret store.
- Pass the same conformance tests as `AnthropicLLM`: plain reply, tool call, tool result round trip, error mapping, usage.
