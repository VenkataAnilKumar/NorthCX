# Feature research: agent platform, user platform and admin platform (November 2026)

Status: research notes, not a commitment. This is the one place in the repository where other companies' products are named; the product itself depends on none of them. **Evidence quality is low to medium:** nearly every source below is a vendor blog, buyer guide or comparison page written to sell something. Treat each claim as "what the market is saying", not as measured fact. The two firmer sources are the OpenTelemetry specification pages and an academic survey of agents in production. Searches were run on 2026-11-09; each ran once, so coverage is partial.

## What the sources agree on

**1. Governance is a buying criterion on par with capability.** Customer-service buyer guides now weigh admin controls, guardrails, audit trails and analytics equally with automation features ([Lorikeet comparison](https://www.lorikeetcx.ai/articles/best-ai-support-automation-platforms-compared-2026), [Decagon enterprise features](https://decagon.ai/resources/enterprise-conversational-ai-features), [Fini governance guide](https://www.usefini.com/guides/ai-support-platforms-governance-approval-controls-audit-logs)). Described features: an admin console showing who uses the AI and for what; role-based limits on which models or features a team may use; conversation-level audit logs; separate models that check the main agent's output against policy before it reaches the customer ([Konverso roundup](https://www.konverso.ai/en/blog/6-best-customer-service-ai-agent-platforms-in-2026)).

**2. The enterprise admin checklist is stable.** SSO plus SCIM (deprovision in minutes, enforce MFA and session rules), a small set of roles (admin, builder, operator, viewer) plus custom roles, an agent registry or catalog (owner, business purpose, environment, model), per-agent budgets and rate limits tied to the agent's identity, and audit events that record user, agent, tool, redacted parameter class, outcome and the approval reference ([Pokee buyer's guide](https://pokee.ai/blog/enterprise-ai-agent-platform-guide), [MintMCP comparison](https://www.mintmcp.com/blog/agent-management-platforms-compared), [Gravitee catalog notes](https://gravitee.io/corpus/gen-948/web-business-management-system/ai-agent-service-catalog-and-lifecycle-management-for-enterprise-web-business-platforms.html), [Jannik Reinhard on a control plane](https://jannikreinhard.com/enterprise-agent-control-plane/)).

**3. MCP is becoming an enterprise requirement, with governance gaps.** The 2026 roadmap lists enterprise readiness and audit trails as a priority; enterprise-managed authorization (access routed through the company's identity provider) was reported as stabilized in June 2026; a July 2026 revision added a stateless Streamable HTTP transport; explicit MCP support is showing up in procurement requirements ([WorkOS on the roadmap](https://workos.com/blog/2026-mcp-roadmap-enterprise-readiness), [CData](https://www.cdata.com/blog/2026-enterprise-mcp-adoption-roadmap), [Snowflake on MCP gateways](https://www.snowflake.com/en/blog/engineering/enterprise-mcp-gateway-ai-agent-governance/)). Several sources warn that MCP is an access layer with weak default governance. These are secondary reports; the MCP specification itself should be read before building.

**4. Telemetry is converging on OpenTelemetry's GenAI conventions, which are not stable.** The agent conventions define `create_agent`, `invoke_agent` and `execute_tool` operations (tool spans named `execute_tool {tool_name}`), and tool failures propagate error status to the parent span. The official pages still mark them as in development, and a June 2026 claim that they were stabilised conflicts with that ([OpenTelemetry agent spans](https://opentelemetry.io/docs/specs/semconv/gen-ai/gen-ai-agent-spans), [GenAI spans](https://opentelemetry.io/docs/specs/semconv/gen-ai/gen-ai-spans), [Honeycomb on agent timelines](https://www.honeycomb.io/blog/instrumenting-ai-agents-agent-timeline-opentelemetry-guide)).

**5. Evaluation practice in customer support: people first, judges calibrated.** A production study of deployed agents reports human review (74 percent) and LLM judges (52 percent) far ahead of rule-based checks (42 percent) ([Measuring Agents in Production](https://arxiv.org/pdf/2512.04123)). Practitioner guidance: calibrate a judge against a few hundred human labels before trusting it; use binary pass/fail for regression gates; put approval gates only on risky, irreversible or customer-facing actions, because a synchronous gate on a 30-second support reply is too slow, so sample and batch-review instead; feed reviewer rejections back into the regression set ([Statsig](https://statsig.com/perspectives/humanloopevals-automationlimits), [n8n playbook](https://blog.n8n.io/production-ai-playbook-human-oversight), [Microsoft Learn module](https://learn.microsoft.com/en-us/training/modules/aaai-design-human-in-loop-approval-workflows/7-summary)).

**6. QA and agent-assist tools score every conversation.** Scorecards, 100 percent coverage instead of a small sample, real-time suggested articles for staff, and QA for AI agents as well as people ([Level AI guide](https://thelevel.ai/blog/customer-support-quality-assurance-tools), [Kaizo](https://kaizo.com/blog/customer-service-quality-assurance-software/), [Typewise](https://www.typewise.app/blog/qa-scoring-platforms-ai-support)). One reviewer notes a leading tool lacks calibration sessions and reviewer assignment, and users report scoring errors needing manual correction (a vendor-written comparison; weak evidence).

## Where NorthCX stands against each theme

| Theme | NorthCX today | In the plan | Possible addition |
|---|---|---|---|
| Admin console and visibility | Studio: keys and roles, audit log, SSO settings, residency, approvals, review | Admin portal app after tenancy; usage and cost per team (E10, WP3.6) | A "who used which agent, for what" view built on audit and traces |
| Roles | Seven roles, hashed keys with expiry and revocation | Keys scoped to agents and environments (WP3.1), groups (WP3.2) | An analytics-only role that sees metrics without agent configuration |
| SSO, SCIM | OIDC with group-to-role mapping | SCIM server (WP3.3), SAML (WP3.4) | Session-length and MFA policy settings in the admin portal |
| Agent catalog | Agents are files and versions | Catalog and teams (WP3.6) | Catalog fields: owner, business purpose, environment, model, last release |
| Budgets | Per-conversation and daily token budgets, shared across processes | Currency budgets (WP1.6), per-team budgets (WP3.6) | Budgets bound to an agent's own identity |
| Audit | Hash-chained audit log of staff actions; status events | | Agent-action records with tool, redacted parameter class, outcome and the approval reference, in one queryable view |
| MCP | Not built | Client and read-only server (E4) | Use the stateless Streamable HTTP transport; plan for enterprise-managed authorization; treat audit as part of the design, not an add-on |
| Telemetry | OTLP and Langfuse export of traces | | Map trace events to the OpenTelemetry GenAI operations (`invoke_agent`, `execute_tool`), marked as following an unstable specification |
| Supervision | Output guardrails, input checks, supervised approvals | | Already matches the "second check before the customer sees it" pattern; document it that way |
| Evaluation | Simulations, judge with calibration procedure (live run pending), conversation review feeding regression scenarios | QA scoring and digests (E7) | Scheduled sampling of routine conversations; threshold sweeps for outliers; reviewer calibration sessions; label a few hundred conversations for the judge |
| Staff workspace and agent assist | Not built | Staff workspace backend (E5) | Suggested knowledge articles beside a conversation as the first assist feature |

## Candidate additions, in the order I would take them
1. **Admin visibility view** from audit and traces (no new storage). Small, directly answers the first buying criterion.
2. **Agent catalog fields** (owner, purpose, environment, model) on agent specs and the agent list. Small; needed before the catalog in WP3.6.
3. **Agent-action audit records** with the approval reference. Medium; strengthens the audit story and feeds the MCP work.
4. **OpenTelemetry GenAI mapping** for the existing OTLP export. Small; low risk if labelled experimental.
5. **Scheduled review sampling, outlier sweeps and reviewer calibration** on top of the review queue. Medium; supports E7 and the judge calibration needed for release.
6. **Analytics-only role.** Small; touches the permission tables and every sweep test.

None of these is started. Anything adopted goes into `08-implementation/NorthCX_Implementation-Plan.md` with a work-package number and a decision-log entry.
